# ADR-IAM-009 — APP-COMMON-R1.2 five binding architecture decisions
Status: ACCEPTED DESIGN / NOT IMPLEMENTED / S2 PENDING
Date: 2026-11-14
Branch: feat/iam-shared-platform
Supersedes R1 open decisions DEC-R1-01, DEC-R1-03, DEC-R1-04, and R1 onboarding/migration ambiguity. ADR-IAM-007/008 remain binding.

## D1. Global access revocation
- Keycloak shared **end-user** realm is credential authority; App Common maintains an authoritative global access-control ledger `subject_access_state(issuer,subject,version,state,updated_at)` with `ACTIVE|BLOCKED`, plus `application_access_state(application_id,version,state)`. This ledger is **not a duplicate user directory** and contains no passwords or business profile.
- The disable operation is durable and auditable, with idempotency key and correlation ID: `POST /api/v1/platform/subjects/{subject}/block` (privileged internal API). Persist BLOCKED + monotonically incremented version first; enqueue Keycloak disable/session logout and versioned signed/authenticated revocation event through outbox. No success response may imply worldwide enforcement until all required API gateways/resource servers acknowledge current version.
- Each API enforces local snapshot of subject block state, application state, JWT signature/issuer/audience/expiry, and domain authorization. **No synchronous App Common call on every request**. Cache snapshots are refreshed by push and periodic reconciliation; if freshness exceeds 30 seconds (initial design target) deny protected requests until refreshed. Event version monotonic, replay-safe, out-of-order ignored. Redis may accelerate distribution but is not sole authority.
- `BLOCKED` state rejects **already issued access JWTs** after enforcement, regardless of JWT cryptographic validity. Revoke Keycloak sessions and refresh tokens as defense in depth. Global state must be checked even for apps that have no local user profile.
- Acknowledge limitations: no literal instantaneous guarantee in disconnected systems. Operation transitions `REQUESTED→STATE_COMMITTED→PROPAGATING→ENFORCED|PARTIAL|FAILED`; `ENFORCED` requires acknowledgements from registered enforcement points or documented fallback that denies access. 30s is a **proposed** bounded-staleness target pending measured tests and S2. Fail closed if state cannot be proven fresh; account for clock skew and partition scenarios. For irreversible account deletion, separate workflow and approvals.
- Local Collectra account/tenant block is Collectra-owned, never changes shared global identity or access to App-B.

## D2. SSO and sessions
- **Web default: BFF (Backend for Frontend)**, confidential OIDC client, Authorization Code + PKCE S256, exact allowlisted redirect URI. Access/refresh tokens stored server-side encrypted at rest; browser receives only opaque `Secure; HttpOnly; SameSite=Lax` session cookie (adjust SameSite for verified cross-site deployments), CSRF protection on state-changing endpoints, server session rotation at login/privilege changes, no tokens in localStorage/sessionStorage.
- Each web app owns its BFF and app session, while Keycloak shared realm provides SSO. A user visits App-B, starts its own OIDC authorization flow, and reuses existing Keycloak browser SSO cookie, without a second registration. Different API audiences enforced.
- **Mobile:** Authorization Code + PKCE S256 in system browser, public client, OS secure credential storage; no embedded webview, no client secret.
- `local logout`: invalidate BFF session and associated refresh-token grant where supported; do **not** silently invalidate all other apps' SSO sessions. Keycloak SSO may remain; re-entering app can sign in again via SSO. `global logout`: Keycloak RP-initiated logout plus app session/back-channel logout where configured; apps must honor shared global block state, and still-valid access JWTs remain bounded by revocation policy. Distinguish logout from global security block.
- Short access-token TTL proposed 5 minutes, rotating refresh tokens and idle/absolute BFF session timeouts (proposed 30m idle, 12h absolute), pending threat-model and UX acceptance. Cookies require correct proxy trust, host-only scope and TLS.

## D3. Notification Service
- R1 channel: **transactional email only**. Client Credentials machine-to-machine; app-scoped template code/version, locale, recipient reference, idempotency key and allowlisted variables. No arbitrary cross-app recipient email, no arbitrary HTML, no public send endpoint.
- Transactionally commit `notification_requests` and `notification_outbox` in PostgreSQL; workers lease with `FOR UPDATE SKIP LOCKED`, bounded retries, jitter and DLQ. Unique `(application_id,idempotency_key)` and payload fingerprint: identical retry returns original ID; changed payload returns 409. At-least-once worker processing, no exactly-once SMTP claim.
- Resolve current verified email via authenticated app-owned resolver immediately before send; record recipient resolution version and minimize PII. **Security/transactional messages** (verification, reset, access/security alerts) may be mandatory subject to applicable law; **optional/promotional messages** require explicit opt-in. Marketing is OUT OF R1; preferences/consent must still be scoped by purpose, application and channel. Unsubscribe never blocks mandatory security notifications.
- States `ACCEPTED→QUEUED→SUBMITTING→SUBMITTED`, then provider-evidenced `DELIVERED|BOUNCED|FAILED`; `DELIVERY_UNKNOWN` on SMTP timeout after potential acceptance. SMTP 2xx means provider accepted, not delivered. `DELIVERY_UNKNOWN` **must not be blindly retried**: reconcile provider message ID/status if available, otherwise hold for operator policy and safe retry approval; expose uncertainty to caller.
- Retry transient failures only when provider nonacceptance is known, exponential backoff with jitter, default **three attempts** (configurable); permanent 5xx SMTP rejection or invalid recipient → terminal FAILED; signed/verified provider callbacks, dedup and out-of-order handling. Immutable template versions, localization fallback, HTML escaping, rate limits, PII retention and audit. SMS/push future, separate acceptance.

## D4. Application onboarding and access
- One Keycloak **end-user** realm for all applications, no realm-per-app. App Common `POST /api/v1/platform/applications` creates `REGISTERED` record and durable provisioning job; reconciler provisions distinct OIDC clients, redirect allowlists, client scopes, resource audience mappers, service identities and ownership tags in existing realm. Only after reconciliation and security checks mark `ACTIVE`; operation 202 is asynchronous, not evidence of readiness.
- Web client is confidential BFF; mobile public PKCE client; API is resource server with strict `aud` and `iss`; machine notifications use dedicated confidential service client. Secrets distributed via secret manager, never in admin list API.
- **Global identity means eligible to authenticate, not automatic business authorization.** First entry to App-B can work with global identity and no local profile or Collectra tenant. If local profile needed, JIT provisioning is idempotent under unique `(issuer,sub)`. Collectra memberships require explicit invite or domain onboarding and tenant checks.
- Application-level suspension denies API/notification access for that app without disabling global account or other apps. Decommission removes app clients only after audited dependencies check, never deletes shared realm/users. Consumer API must reject tokens for other audience.

## D5. Collectra migration without changing business identity
- Preserve legacy Collectra user UUID, all tenant/organization IDs, membership rows, business roles, FK references and history. Add **separate** verified `identity_links(issuer,subject,collectra_user_id,verified_at,status)` table with unique `(issuer,subject)` and unique `collectra_user_id` for active one-to-one mapping. No replacing local UUID with Keycloak sub.
- Explicit proof of ownership: authenticated existing Collectra session + Keycloak verified authentication (or operator-reviewed recovery with strong evidence). **Email match alone never links or merges accounts**. Cross-account collision fails closed to manual review.
- Sequence: inventory + immutable backup; PostgreSQL schema migration; dual-read of verified links behind feature flag; test migration in shadow environment; verified link creation under transaction with uniqueness; reconcile all existing FKs and memberships; time-bound cutover to Keycloak JWT; revoke legacy sessions/tokens; disable legacy login; audit and monitor.
- Rollback: before final cutover, feature flag reverts authentication routing without deleting identity links or altering business rows. After legacy credentials/tokens revoked, **do not silently re-enable insecure legacy authentication**; recovery requires approved incident procedure. No auto-creation of Collectra tenant or membership on SSO alone.

## Mandatory proof gates
- REV-01 block global account; previously issued JWT rejected by Collectra and App-B within measured propagation bound, including stale cache and event loss; unrelated user unaffected.
- REV-02 local Collectra block does not affect App-B.
- SESS-01 BFF browser cannot access tokens; CSRF, cookie scope, rotation, logout; SSO works across apps.
- SESS-02 local logout and global logout demonstrate different semantics; mobile PKCE works without client secret.
- NOTIF-01 idempotent submission, outbox recovery, SMTP accepted/timeout/4xx/5xx, DELIVERY_UNKNOWN no blind resend, consent.
- APP-01 client/audience creation in shared realm; wrong-audience rejection, no tenant required for App-B; suspension/decommission preserves shared users.
- MIG-01 real PostgreSQL fixture preserves Collectra UUID, tenant memberships, roles and FKs; email collision rejected, interrupted migration recoverable.
- All tests must be executable on real Keycloak/PostgreSQL and deterministic SMTP fixture, with CI run IDs and independent S2 review. **No tests or runtime behavior claimed implemented by this ADR.**
